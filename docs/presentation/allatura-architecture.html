Allatura is a multi-tenant SaaS for construction commercial controls. This is the system we actually built and deployed. The frontend is a Next.js app deployed on Vercel at allatura.com. It never talks to the backend directly — every call goes through a same-origin BFF proxy that attaches the auth token server-side. The backend is a NestJS REST API deployed as a container on Google Cloud Run, versioned under /v1, with Swagger at /api. Data lives in MongoDB Atlas across twenty tenant-scoped collections. Documents upload straight to Google Cloud Storage via short-lived signed URLs, so our API never handles file bytes. Identity is Auth0, billing is live Stripe, email is Mailgun. The key shape to notice: two clear platforms — Vercel for the frontend, Cloud Run for the backend — and the proxy as the single controlled path between them.

Let's trace one real request. A user logs in on allatura.com; we redirect to Auth0 Universal Login. On callback, our server seals the tokens in an encrypted, httpOnly cookie — the access token is never visible to JavaScript. When the app calls /api/v1, the BFF proxy forwards that token as a Bearer. On the backend two things happen in order. Authentication: the RS256 signature is verified against Auth0's public JWKS. Then authorisation — and this is the important decision — role, status and tenant are read from our database, never trusted from the token. A tenant-scope check rejects any cross-org access with a 403, and a jwtVersion lets us revoke a user instantly. Two supporting flows: onboarding, where the first user becomes owner and invites teammates by email through Mailgun; and billing, where Stripe posts to a signature-verified webhook — Stripe is the source of truth and retries, so billing is eventually consistent. One line to remember: authentication is who you are; authorisation, enforced in our database, is what you can do.

Finally, why it's built this way — four decisions, each with a benefit and a cost. One: identity on Auth0 with RS256, and we keep the token out of the browser via the proxy. That makes tokens XSS-safe and gives us SSO and MFA for free; the cost is an extra hop and a dependency on Auth0. Two: roles and tenant are resolved in our database, not from the token — so a stolen token can't escalate privileges, we have a single source of truth, and we can revoke instantly; the cost is a cached database check per request. Three: a multi-tenant modular monolith on Cloud Run — one cheap deployment, fast iteration for a small team, and scale-to-zero; the cost is a shared blast radius and cold starts. Four: we offload billing to Stripe and files to Cloud Storage, and precompute project financials so dashboards read instantly; the cost is eventual consistency and external dependencies. The through-line is the principle on the left: we optimised for security and speed, and we know exactly what we'd harden first as we grow.
